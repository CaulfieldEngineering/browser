# Browser

Joe's own iPhone browser, a prototype. Joe, 2026-10-29: "Go ahead and build a prototype. For now just a basic, clean sleek browser." Where it is going (HQ/aspirations.md, "our own iPhone browser"): TechLockdown blocks the Safari and Chrome apps so this is the only way onto the web, and its rules come from the mini PC and change with conditions (time of day, the Morning Check-In, focus sessions). None of that is built yet. This app loosens nothing; it is only a browser.

## What it does

- Laid out like Chrome on the iPhone (Joe, 2026-10-29: "I'd actually like chromes layout please"), dark, in the house style (HQ/agent/app-design.md): a top bar with back, the address pill (the site centred at rest, the whole address while typing, share inside it on the right) and a ••• menu (Forward, Reload or Stop, New Tab, Close Tab, Share, the version and Update when there is one, with a green dot on •••); the page in a card with rounded bottom corners; a bottom toolbar of three labelled buttons: **Ask HQ** (opens the HQ app, `hq://chat`), **New Tab**, **All Tabs** (the count in a rounded square).
- Text that is not an address searches DuckDuckGo with SafeSearch strict (`kp=1`).
- Tabs (`Tabs.swift`): All Tabs shows every tab as a card with its snapshot and title, two across; tap to open, x or a sideways swipe to close, + for a new tab, Done or the open tab's card to go back. A long press on All Tabs: New Tab, Close This Tab. Links and scripts that open a window open a new tab. Tabs, their addresses and snapshots persist across launches; a tab's web view is made only when it is opened, background tabs give theirs up when memory runs low, and at 30 the least recently used closes. No private tabs.
- A thin green progress line under the top bar, swipe from the edge for back and forward, pull down to reload.
- Picture in picture and sound in the background: `allowsPictureInPictureMediaPlayback`, the audio session in `.playback`, `UIBackgroundModes` audio. A site that pauses itself when the page is hidden still does.
- An updater: on opening it reads the install page's `version.json`; a newer build shows a green Update capsule (and a line in the menu) that installs from the install page. A small x beside the capsule puts it away for that version (the menu line and its dot stay; the next version shows the capsule again).
- Links that would hand off to another app stay in the browser (universal links are not followed out). No private mode, no downloads, no setting for DNS or proxies.

## The policy: one place every navigation passes through

`ios/Browser/Policy.swift`. `Policy.decide(request:isMainFrame:)` sees every request before it is made, and `Policy.decide(response:isMainFrame:canShow:)` every answer before it is shown; both return `allow`, `openOutside` (tel, mailto, sms, FaceTime go to the system) or `block(title, reason)`, which shows a calm page over the web view with Go back. The rules from the mini PC will plug in there. For now it blocks:
- configuration and provisioning profiles, apps and installers, by file extension or MIME type (`.mobileconfig`, `application/x-apple-aspen-config`, `.ipa`, `.mobileprovision` and the like);
- `itms-services` app installs (sideloading from a web page), with one exception: an `itms-services://?action=download-manifest` link whose `url` is exactly `https://caulfieldengineering.github.io/<browser|hq|blocks>-install/manifest.plist`, our own install pages (`Policy.isOwnInstall`). Every other scheme that is not the web (`itms-appss://` for the App Store, an app's own link) opens that app, the way Safari does (Joe, 2026-11-03, after the Canon R50's QR code was stopped on its way to the App Store: "The refusal to redirect was never a spec of mine");
- downloads in general (anything the web view cannot show), since the prototype keeps no files.
- image and video search, always, with no switch (Joe, 2026-11-04: "all that stuff I looked at I want to stop"): the image and video tabs of Google (`tbm=isch`, `tbm=vid`, `udm=2`, `udm=7`, `images.google.*`, `/imghp`, Lens, search by image), DuckDuckGo (`ia`/`iax` = images or videos, `i.js`, `v.js`), Bing (`/images`, `/videos`), Yahoo, Yandex, Ecosia, Brave, Startpage, Qwant, Mojeek, AOL and Baidu, Pinterest search, and reverse image and face search sites (TinEye, PimEyes, FaceCheck and the like). The page says "Image search is off here". `ios/Browser/SearchBlock.swift` has the list; a page that switches to its image tab without navigating (DuckDuckGo) is stopped when its address changes, and content rules refuse the requests for image results. Normal web search is unchanged. Tests: `ios/BrowserTests/SearchBlockTests.swift`.

## The Instagram filter (2026-11-05)

Joe, 2026-11-05: "I'm more interested in filtering out suggestive content", then, before it was built: "Let's just try the suggestive content for now and we can build on it". On instagram.com, in every tab, suggestive posts and Reels are removed outright: not blurred, nothing to tap to see them, no setting and no switch. Feed, Reels, messages, profiles and posting stay as they are. Nothing about it is sent off the phone.

- **Where**: `filter/shared` (shared with the laptop filter, which is packaged elsewhere): `rules.js` (the rules, a list: a text rule on the caption, hashtags and alt text; an image rule on the classifier's scores; a later rule such as ads or suggested posts is one more entry), `ig-filter.js` (the page side), `classifier.html`/`classifier.js` (nsfwjs, MobileNetV2, MIT, vendored in `vendor/`), `bridge-ios.js`. In the app they are the folder `shared` (`ios/project.yml`), run by `ios/Browser/Filter/InstagramFilter.swift` at document start in a content world of their own (`igfilter`), so Instagram's scripts cannot see or undo them.
- **Surfaces** (2026-11-05, after Joe: "Reels also need filtering ... their reels pages are still full"): the feed, post pages, profile grids (posts, reels, tagged), Explore and search grids, the reel viewer, stories and messages. A grid or reel tile whose picture is an inline CSS `background-image` (Instagram draws reel tiles that way) is held and judged like an `<img>`; avatars and story rings only when shown 120 px or larger. A hidden reel or story takes only its own box (the box climbed to holds one picture and one video at most).
- **How a post is judged**: pictures from Instagram's CDN are held invisible until judged. The app fetches the same picture (only `cdninstagram.com` and `fbcdn.net` hosts), makes it small, and the classifier page, in a hidden one-point web view loaded on the first question, scores it. A flagged picture hides its post (the `<article>`, the grid tile, or the Reel's container; in messages only the picture) without a word (Joe, 2026-11-05: "i'd prefer not to label the pictures. Keep it more discrete"): in the feed and the reel viewer it collapses as if it were not there; in a grid the tile stays as a plain blank of the same size in the page's own colour, so the grid does not reflow. A blank tile cannot be tapped and there is nothing to reveal. A picture that could not be judged yet (the model still loading, a picture that would not load) is hidden the same way and tried again at 5, 20 and 60 seconds: it fills in quietly once judged clean and stays hidden if it never is. Why a post was hidden is only counted on the phone, never shown. The classifier judges one picture at a time (a feed asks for dozens at once), the app fetches each picture as Safari would with three tries, and the Instagram app loads the model at launch.
- **Revealing clothing** (0.1.48; Joe, 2026-11-05: "Can we try upping the filtering on instagram? Like, shorter tank-tops, bikinis, gymwear etc."): a second judge beside nsfwjs, any person (gender detection skipped, as agreed). TinyCLIP-ViT-40M-32-Text-19M-LAION400M (Microsoft, MIT), its vision tower exported to ONNX and quantized to int8 (`vendor/tinyclip-vision-int8.onnx`, 40 MB), run with onnxruntime-web (MIT, `vendor/ort/`, one thread) in the classifier page (`clip.js`), against prompts embedded once offline (`vendor/clip-prompts.json`: bikinis and swimwear, lingerie, crop and short tank tops, sports bras, tight gymwear, fitness posing; against everyday clothes, people working out in loose clothes, landscapes, empty beaches, gym equipment, music gear, products, food, text). Hidden from 0.6 (`filter-config.js`). On a check of public-domain photos revealing ones scored 0.86 to 0.99 and everyday ones 0.36 or less. Plus words and tags (#gymgirl, #fitgirl, swimwear and the like; ordinary gear words left out). A picture counts as judged only when both judges answered. The classifier page is served under `igc://local/` (`BundleFiles`) so it can fetch its model files.
- **Explore and search** (0.1.48; Joe: "let's get rid of the explore page", "get rid of all of the junk and images that come along with the Instagram search page"): on /explore and below, only the search field and a plain list of accounts and hashtags; each result's small avatar (44 pt or less) stays and is judged; videos, larger pictures, post and reel tiles, the suggested / trending / discover sections and the Top / Reels / Places tabs are gone (`ig-tidy.js`). On a wide screen the Explore link goes too.
- **The Following feed** (0.1.55; Joe: "I follow like 1000 people but every time I open it I see the same exact post"): Instagram's home is always `/?variant=following`, the accounts he follows in time order. Natively every main-frame load of `/` without a variant is rewritten (`Flavor.followingFeed`: launch, links, pull to refresh; not Back); in the page `ig-tidy.js` does the same on arriving, on a tap of the home tab or logo, and when Instagram changes the address to `/`. A variant already named (favorites) is left alone. Test fixtures are served at the Following feed for that reason.
- **Posts already seen, skipped** (Joe, 2026-11-10: "Could we add a setting in our IG app to note what we see and not show me literally the same posts every time I open the app"; `filter/shared/ig-seen.js`): on the home feed, a post on screen (half or more) for a second is noted by its post id with the time, in the page's own storage, so per account, on the phone only (at most 6000, 30 days). The next fresh open of the feed (launch, the home tab, pull to refresh) takes out every post noted before that load, the filter's way (one invisible pixel, so the next posts load); posts seen during the visit stay, so scrolling back and Back still find them. Profiles, post pages, messages and Reels are untouched. The switch is the Instagram app's menu, "Skip posts I've seen: On/Off" (`SeenPosts`, on unless turned off; the page asks `IGFilterBridge.seenOn()` before skipping anything and hears `igs-on`/`igs-off` at once). Counted as "Seen before, skipped" in Filter today. **Repeats** are skipped always, not by the setting (Joe, 2026-11-10, with a screen recording of the same four posts coming round again and again: "stuck in some cyclical loop when scrolling"): a feed post whose id is already on the page above it is taken out the same way. Where there is no bridge (the laptop) it is on. Tests: the "seen:" lines in `filter/test/ig-filter.test.mjs`.
- **Hide a picture** (the menu's Tools; Joe, 2026-11-12: "I click it and then I have to click the picture but it doesn't hide anything"): the page is dimmed a little with "Tap a picture to hide it" at the top; every touch, pointer and mouse event is stopped at the window (the page's first listeners, added at document start) so Instagram never sees the tap, which used to be taken by its clear box over each picture (double-tap to like) and never became the click the old version waited for. The tapped picture's post (or, in a story or reel, that slide) goes at once and is remembered on the phone; the page says "Hidden", or "No picture there", and picking ends (or lapses after 20 s). Works in stories: the tap neither closes nor advances the story; the viewer then goes on as for any hidden story.
- **The two-finger tap** that opens the menu never reaches the page past the first finger: from the second finger until every finger is up, and for 0.6 s after, touches, pointer and mouse events and clicks are stopped (Joe, 2026-11-12: "when I two finger tap in a story it closes the story").
- **The reel and story viewers: covered, not removed** (Joe, 2026-11-12: "A lot of times when it blocks a slide too it completely shuts down the app. Like grey box."): a hidden slide keeps its box and its pictures and video are made invisible over black; a slide's box never climbs to the page's main area, tab bar, a dialog or Instagram's root (a video story with only its avatar beside it used to take Instagram's whole app with it, `display:none`, a grey screen). The viewers reuse their boxes, so a slide hidden for one picture is let go when the next story's picture arrives in it, and that one is judged on its own. If the page's process ends anyway, it is counted (`page-restarted`) and reloaded; twice within 20 s, the app's home opens instead.
- **The order pictures are judged in** (Joe, 2026-11-12: "I spend most of my time looking at empty grey boxes"): the judge takes one picture at a time and the feed asks for dozens (every carousel slide, posts below the screen), and the ones on screen used to wait behind all of them. The page now keeps the queue, three in flight, and always sends the picture nearest the screen next (on screen, then just below, a carousel's next slide, then the rest); the classifier runs its two judges at once (the GPU one and the CPU one). Nothing shows before it is judged. `node filter/test/ig-perf.bench.mjs` measures it on a feed shaped like Instagram's with a judge as slow as the phone's: pictures on screen after a scroll waited about 4.5 s, now about 0.7 s.
- **Settings** in one file, `filter/shared/filter-config.js`, read by the filter on every device and by the Devices dashboard (Filters).
- **Counts on the phone** (`FilterStats`, the menu's "Filter today"; in the Browser "Instagram filter today"): per day, how many posts were hidden by reason (picture, and which part of the line: suggestive, explicit or combined; caption; not checked, and why), how many were shown again after checking, and how the model runs (WebGL or CPU, load time, time a picture). No pictures, no addresses, nothing sent anywhere. Thresholds and words are not changed from these counts without Joe (locked memory). A video is judged by its poster and a drawn frame before it shows, then every two seconds while it plays (a drawn frame, or a snapshot of the web view where the frame is cross-origin).
- **Known misses**: pictures drawn by a stylesheet rather than inline (not seen on Instagram so far); the first moments of a video whose frames cannot be read in the page; posts the model scores low (it judges pictures, not intent).
- Tests: `node filter/test/ig-filter.test.mjs` (Chromium, a fixture page served as instagram.com and the real classifier) and `ios/BrowserTests/InstagramFilterTests.swift` (the simulator: the files are in the app, only Instagram's hosts are fetched, the model scores a plain picture, a suggestive caption is removed in the app's own web view, other sites are untouched).

## The blur filter (removed 2026-11-04)

A scheduled on-device filter that masked people in images and video during windows Claude published to `blur.json` existed from 2026-10-30 to 2026-11-04 (last used the night of 2026-11-03, until 6:00 AM). Joe, 2026-11-04: "Get rid of the blur altogether." It is gone from the app: no Vision processing, no schedule fetch, no media gate. The install page keeps `blur.json` as `{"windows":[]}` so an older build that still reads it stays off. The last code is in git history (the parent of the removal commit) and on the unmerged branch `codex/scheduled-blur`, which also holds an unshipped thumbnail fix and an erase-the-body look.

Do not call the WebKit Swift overlay's `Result` APIs (such as `evaluateJavaScript(_:in:in:completionHandler:)` with a `Result`): with the 17.0 deployment target they link `/usr/lib/swift/libswiftWebKit.dylib`, which iOS 18 does not have, and the app aborts at launch (2026-11-03). Use the Objective-C entry points (`__evaluateJavaScript(_:inFrame:in:completionHandler:)`).

## History and the feed to the mini PC

Joe, 2026-11-03: "Are you able to log my browser history from our app?", and what for: "Both mainly adaptive accountability". `ios/Browser/History/`.

- **History** (••• menu, History): every main-frame page a tab opens (time, address, title), newest first under a heading per day, with a search field; tap to open in this tab, long press to open in a new tab or copy the link. Pages that did not open are listed, muted. Kept on the phone in Application Support, one JSON line per visit and one file per month (`HistoryStore`), written only by appending. There is no switch to turn it off and nothing in the app that deletes it.
- **What counts as a visit** (`HistoryRecorder`, attached to every tab's web view): each new main-frame address, full loads and single-page sites changing their own address. It is written once the title comes (1.5 s more for it to settle), after 5 s without one, or when the tab moves on; a redirect hop (gone within a second, still loading, no title) is not one. A failed load or a page the policy does not open is a visit marked as not opened.
- **The feed** (`Feed`): each visit, and a **heartbeat** (on coming to the front, every five minutes while in front, on leaving), goes into a queue kept in a file and is sent in batches of up to 200 to the HQ service on the mini PC (`hq-widget` `server/browser-feed.js`, `POST /api/browser/feed`), by its Tailscale name over HTTPS through the service's CONNECT tunnel on `100.92.203.47:4400`, the way the HQ app reaches it. Offline, it waits; after a failure it tries again after 5 s, 15 s, 1 min, 2 min, then every 5 min, and at once when the network comes back or the app comes to the front. Sending never blocks browsing. The key for the feed is asked for and kept in the Keychain by itself (`POST /api/browser/pair`; the key is good for the feed only, and a revoked one is replaced). Every event has a sequence number kept in the Keychain with the install's id, so a reinstall continues the numbers and the mini PC sees a gap if a queue was lost. The heartbeat lets the mini PC tell "not browsing" from "the feed stopped".
- On the mini PC the events are kept append-only in `C:\Users\Joe\.held\browser` (outside Dropbox and git), and the laptop watch reads them too.

Tests: `ios/BrowserTests/HistoryFeedTests.swift` (the store, the queue's numbers across a reinstall, batching, retry and backoff, a replaced key, the heartbeat, what counts as a visit) run on the iPhone simulator in `ios-build`.

## Building and installing

The same route as the HQ and Blocks iPhone apps. `.github/workflows/ios-build.yml` runs on a push to `main` touching `ios/`, tests or the workflow (or Run workflow): the iPhone simulator tests must pass, XcodeGen makes the project from `ios/project.yml` on a macOS runner, then archive, ad-hoc export, and `app.ipa`, `manifest.plist`, `version.json` and the install page go to the public repo `CaulfieldEngineering/browser-install`, served at **https://caulfieldengineering.github.io/browser-install/**. Versions are `0.1.<run number>`. The repo is public, so these Actions builds are free. Manual runs from any other branch (Run workflow) build and test but cannot sign or publish; validate a candidate there before advancing `main`, and never use TestFlight as a compiler.

Signing: Blocks' Apple team (`D56QY8C7WL`), App Store Connect API key and Apple Distribution certificate, with the browser's own App ID `com.caulfieldengineering.browser` and ad-hoc profile `Browser AdHoc`. `node scripts/apple-provision.mjs` makes the App ID and the profile (into `C:\Users\Joe\.apple\browser`, never a new certificate); `npm i --no-save libsodium-wrappers && node scripts/apple-secrets.mjs` puts the certificate, its password, the profile, the team and the install repo's deploy key (`C:\Users\Joe\.apple\browser\install_key`) in this repo's Actions secrets. Every year, after Blocks' certificate is renewed, run both again, then the workflow, then reinstall.

Joe installs it: Safari on the iPhone, https://caulfieldengineering.github.io/browser-install/, Install.

## TestFlight (for the default browser permission)

Apple assesses the default browser permission only for an app on the App Store or on TestFlight (2026-10-29), so the browser also goes to TestFlight with a public link. Nothing is submitted for App Store review. The app record is **CaulfieldBrowser** (SKU `browser-001`), made by Joe in App Store Connect.

- `node scripts/apple-testflight.mjs profile` makes the App Store profile `Browser AppStore` (same certificate), then `node scripts/apple-secrets.mjs IOS_APPSTORE_PROFILE_BASE64 ASC_KEY_ID ASC_ISSUER_ID ASC_KEY_P8_BASE64` puts it and the API key in the secrets.
- `.github/workflows/ios-testflight.yml`, run by hand only: archive with the `APPSTORE` flag (no install page updater and no install links in that build), export for App Store Connect, upload. Version `1.0`, build number = that workflow's run number.
- `node scripts/apple-testflight.mjs builds` until the build is `VALID`, then `beta` (the external group `Public` with a public link for 10 testers, the test notes, the review notes, beta review), and `status`.
